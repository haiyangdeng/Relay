# Relay 双架构统一开发

用户要求：以后所有功能开发和问题修复，Intel 与 Apple Silicon 两个版本都要同步，不能只改其中一个版本。

## 实现要求

- 先把需求转成可验证的行为，并检查两个架构对应的入口、数据和运行链路。需求或版本基准不明确时先确认，不猜测另一个版本的行为。
- 业务逻辑、界面、模式切换、配置格式和修复优先共用同一份实现。CPU 架构差异只用于确有必要的二进制选择、原生编译及平台适配；不能按架构隐藏或削减功能来绕开故障。
- 一个架构发现的问题，要检查另一个架构的同类路径并同步修复。修改仅覆盖当前需求，不顺手改无关代码。
- 区分代码缺失、运行资源缺失和未启动状态。代理节点选择、测速以及规则／全局／直连模式须分别验证真实行为，不能以按钮出现或打包成功替代功能验收。

## 验证与交付

- Bug 先用有效用例复现，再验证修复；共享回归不应无理由写死 arm64 或 x64。原生检查选用当前架构对应的固定资源，保留摘要、架构、签名和归属校验。
- 与本次修改相关的共享测试、类型检查和构建检查须通过；涉及架构相关资源或原生运行的功能，分别记录 x64、arm64 的构建和实际运行结果。
- 交付两个版本时，使用同一源码快照、相同版本号和构建号，核对两份安装包的业务代码及功能清单一致；只允许有解释的架构资源差异。构建方法见 [BUILD](../../../docs/BUILD.md)，发布方法见 [RELEASING](../../../docs/RELEASING.md)。
- 缺少某架构实机时，继续完成可验证的工作，明确记录该架构尚未实测的项目。交叉编译成功或另一架构通过，不等于双架构实机验收通过；不能把只验证一个版本报告为全部完成。
- 修复和重装前保留用户的配置、订阅与必要资源；测试结束核对约定的代理状态，避免用删除用户数据掩盖问题。

这些要求不额外授权上传、发布、修改系统权限或替用户确认 macOS 管理员授权。
